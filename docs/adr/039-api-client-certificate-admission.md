# ADR 039: opt-in API client certificate admission

Accepted for implementation 2026-11-05; extends ADRs 035–038. Implements the API receiver boundary only. Managed client identity issuance/delivery, an authenticated web-to-API deployment, PKI rotation/revocation and service launch remain unfinished. No web secret or AWS permission is added; no certificate grants user/tenant authority. Exact execution/reviews belong in progress.

When API server TLS is enabled, optionally enable `Deployment:ApiTls:ClientAuthentication:Enabled` with a separate `CaSha256` and one-to-four contiguous, distinct, canonical lowercase SHA256 `LeafSha256:0..3` public certificate fingerprints. Reject malformed/unknown/scalar/nested/disabled-but-populated settings and sparse/duplicate pins. Anchors come only from fixed `/opt/saveit/trust/client-ca.crt`, validated through the existing bounded same-file public CA/complete-DER/hash parser. Its new owned collection return transfers imported public certificates without reopening input. The API transport lease retains those immutable anchors through host shutdown, then disposes them and the server certificate.

Configure Kestrel RequireCertificate, a five-second TLS handshake timeout, TLS1.2/1.3 and native custom-root chain policy **before the initial chain build** through OnAuthenticate. Disable AIA downloads, renegotiation and TLS resumption; keep revocation mode NoCheck because no managed offline/online revocation infrastructure exists. Require no chain/policy errors, current leaf validity, an explicit non-CA constraint, DigitalSignature without KeyCertSign, exclusive clientAuth EKU and RSA2048+, plus an exact approved DER certificate fingerprint. This initial mode does not support EC client keys or arbitrary EKUs. No forwarded certificate header, request identity field, platform root or accepted CA alone grants admission. Fingerprints identify only the administrator-reviewed peer certificate and require matching private-key possession in the real TLS handshake; they are not signatures or tenant principals.

Before routing/response registration, recheck actual TLS certificate expiry and pins on each HTTP request, including keepalive. A valid TLS peer remains anonymous until the existing cookie/Okta adapter and live membership/organization policy authorize it. Certificate rejection grants no HTTP access, and per-request failure is a body-free403/no-store. Keep the health-only literal IPv4 loopback8080 exception for GET operational probes; all other plaintext routes remain denied. Readiness over TLS requires a client certificate. TLS does not recall completed responses or revoke an old instance's immutable pin set; drain/fence/restart and managed retirement remain gates.

Add a separate public-only `saveit-client-trust` named image context, exclusive fresh-directory preparer and unconfigured placeholder. Only API copies client-ca.crt, root-owned0444; web/worker/deployment receive none. The ordinary public trust preparer also refuses any existing output directory, including unrelated files, to avoid accidentally submitting private leftovers as a public build context. Both helpers copy only validated public bytes and emit hash-only manifests/fixed failures. These checks do not attest local operator intent or prevent privileged post-validation mutation; immutable images/no replacement mounts remain the consumption boundary. Public certificate extension content still requires review, not a DLP claim.

The unapplied cloud API task now declares client authentication enabled **without pretending delivery is finished**. It intentionally cannot start until reviewed public client anchors/pins and a real authenticated client carrier are bound. No client private key/payload/secret selector or web IAM grant enters Terraform. Existing six API configuration-secret fields and retired session pairs remain unchanged. Protected preflight still validates that existing secret carrier, not the new public runtime metadata or an actual peer's PKI. Current DNS/SG outputs remain metadata, not authentication or launch approval.

Synthetic Linux CI builds with a separate client CA, retains normal web/identity/recovery/access/outage flows in server-TLS mode and starts an additional opt-in API instance for receiver canaries. An isolated Node test client reads only synthetic private fixture files as their host owner; the ordinary web service receives none. Test approved/rotation clients, no certificate, same-CA unapproved leaf, pinned foreign issuer, pinned expiry, an unpinned server-purpose leaf, forwarded-header refusal and valid-client/anonymous-user401. That packaged server-purpose refusal does not isolate EKU enforcement: direct leaf and native-chain tests separately reject a pinned server-purpose certificate (NotValidForUsage). Unit/native Kestrel tests also cover leaf usage/strength/validity/configuration, pre-native chain options, actual same-connection expiry403, immutable in-memory anchors and public context preparation/refusal. This is synthetic receiver evidence, not a deployed managed identity/client or certificate lifecycle.

No application API schema, migration, tenant/membership/organization authority, forced RLS, audit/outbox, worker privilege or response-drain protocol changes. Preserve the entire enterprise roadmap. Next: choose/implement a client identity carrier consistent with web's lack of secret authority, bind cloud public metadata, implement authenticated ingress/services/registry health/drain and protected operations, then verify real IAM/PKI/rotation/recovery in authorized staging.
