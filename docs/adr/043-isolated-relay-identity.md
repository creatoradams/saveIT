# ADR043: isolated relay identities and staged repository admission

Accepted for implementation 2026-11-07; extends ADR031/032/042. This is unapplied infrastructure metadata, not a launched relay, populated secret, SDK loader or managed authorization evidence.

The credential-owning relay must never reuse migration/access roles just because it shares their deployment image. Keep the existing five workload task/execution identities and selector contracts unchanged. Add a separate relay-identity root declaring its own task/execution pair, configuration/log rotating protected keys, configuration-secret metadata and protected finite-retention operational log group. No secret-version/value resource/data lookup, payload input/output or account operation is introduced.

Reserve task authority for a future in-process SDK startup read of one whole JSON secret at its exact ARN/UUID over TLS in the configured region. Decrypt is limited to its configuration key via regional Secrets Manager, exact caller account and SecretARN/SecretVersionId encryption context. Explicit missing/wrong version denies prohibit silent AWSCURRENT fallback. Custodian validation uses a different service version context and is not constrained by the task-only pin. The future loader must validate returned ARN/version and original bounded bytes before starting the existing relay, with sanitized failures and no payload environment/CLI/logging. This decision defines authority only; delivery implementation is separate.

Execution gets exact deployment-repository pull, regional registry authorization, own log-stream writes, own log-key crypto via regional Logs/account/exact group and separate via-Logs DescribeKey without encryption context. It receives no secret/configuration-key authority. Task receives no ECR/log/EFS/database/operator authority. Complete permissions-boundary explicit denies constrain additional identity/session grants; grants remain separate inline policies. ECS trust requires the exact service, account and regional SourceArn wildcard; scheduler/PassRole controls remain future work. IAM identities never change live membership/organization/tenant/RLS/audit/response-completion authority.

Avoid a cross-root creation cycle: relay bootstrap with image_repository=null creates protected metadata/roles but both boundaries deny all AWS actions and no inline grant exists. Add nullable exact artifact-stores.relay_execution_role_arn; its null preserves legacy readers. A bound canonical role is added only to the deployment pull allowlist in that single existing repository-policy owner. Publisher/control/delete/TLS denials and resource counts remain unchanged. Feed that actual repository output back into relay-identity, requiring exact same-account/region/cell/environment ARN/URL and exactly three distinct migration/access/relay execution reader references before grants activate. binding_ready describes this declared contract only; it does not inspect real IAM drift or prove runtime pull/read/launch. A null withdrawal plan retains stores/roles but is not applied revocation/fencing proof.

Use bounded exact same-account administrator/custodian inputs excluding all twelve workload names, including case variants. They remain trusted controllers able to change policies; UpdateSecret can also write a payload. Custodian restrictions are not exclusive-writer or human/transitive-isolation proof. Key context uses the exact service-generated six-character secret-name slot to avoid a key/secret/role cycle; runtime policies use the resolved exact ARN. Keep destroy guards, thirty-day recovery/deletion windows, distinct keys, rotation and finite operational retention. Operational logs are not immutable tenant audits.

One compatibility gate is deliberately unresolved before apply: the log key requires customer kms:CallerAccount even for the direct regional Logs service-principal path, separately from forwarded-role calls. The published CloudWatch example uses regional service and exact group context without that account condition; KMS documents CallerAccount for IAM user/role callers. No current managed evidence establishes its availability on every direct call. Missing context fails closed and may block service operation. Obtain authorized managed context/DescribeKey/PutLogEvents evidence or a separately reviewed account-bound service-policy design before apply; synthetic contexts must not be presented as proof. Do not silently relax the existing caller/account/service/group boundaries.

Account-free native plan tests include independently reviewed complete policy JSON (every action/resource/effect/principal/condition and all explicit denies), narrow positive/missing/wrong condition predicates, invalid inputs, distinct-key checks, maximum accepted trusted-role lengths and actual staged artifact-stores module contracts. Preserve pinned Terraform/provider/action hashes and lockfiles. Full CI still runs PostgreSQL, browser, packaged TLS/recovery and source/image gates. Mocks are not an IAM simulator. Exact tests and reviews remain in [progress](../progress.md).

Next implement SDK startup delivery and private endpoint admissions for execution ECR/Logs versus task Secrets Manager, then referenced network/discovery, isolated task/service bindings and protected launch/health/drain/fencing. Existing runtime-endpoints includes legacy execution roles only and must not be assumed sufficient. Managed PKI/IAM/network/Okta/RDS, secret population/rotation, signing/promotion, multi-instance keys/recovery, quotas/SLOs and full enterprise scope remain unfinished. No AWS credential/API/apply, real payload or public deployment is needed for this slice.
