# ADR 024: offline-tested AWS state bootstrap

Accepted for implementation 2026-11-01. Extends ADR 004. No AWS account/API/apply or deployment is authorized or performed by these definitions.

The first infrastructure implementation is a separate state-bootstrap root. Pin the official AWS provider and commit its verified dependency lock, including Windows/Linux checksums. Native mocked-provider plan tests run without credentials and assert configuration boundaries. They do not establish real AWS permission or service behavior. The application cell remains separate unfinished infrastructure.

Require an explicit commercial AWS account, region and bounded same-account IAM role ARNs for state operators and key administrators. Use short-lived SSO/assumed-role credentials externally; never put credentials or secret values in Terraform inputs/state. The bucket is private, owner-enforced, versioned, KMS-encrypted and protected against accidental Terraform destruction. The KMS key rotates and has a thirty-day deletion window. Explicit bucket policies deny insecure transport, unexpected principals and conflicting encryption choices; state deletion is not granted to normal state operators, while lock-file deletion is. Key use is limited to this bucket through regional S3. Account-root delegation/key administration remain privileged recovery boundaries, not tenant authority.

An explicit KMS request must supply the selected key ID; otherwise S3 can choose its AWS-managed key rather than the bucket default. Fully absent encryption headers retain that default. Bucket/key control-plane mutation is explicitly denied to nonadministrators, even when a broader identity policy would grant it; lifecycle changes can otherwise defeat object-deletion denial. Administrators/root remain a higher trust boundary. Mocked tests check the actual policy conditions and a narrow documented header truth table; they are not a general IAM evaluator.

Use separate named state keys for bootstrap and each cell/environment, with native S3 lock files. No workspace-based state expansion or DynamoDB locking is introduced. Bootstrap initially uses ignored local state; only after an authorized account bootstrap may an ignored backend override migrate that state into the protected bucket. Backend examples contain identifiers only. Review the plan, principals, region/residency, budgets, CloudTrail access auditing and break-glass/recovery ownership before any apply or remote-state migration.

Provider mocks, encryption settings and versioning are not applied resources, immutable/offsite backup or a recovery drill. KMS key/policy lockout, state version recovery and actual least-privilege behavior must be tested in the authorized account. Networking, managed database, runtime secrets/keys, registry/promotion, services/ingress and operational controls remain further work; do not call the cell deployable from this bootstrap alone.
