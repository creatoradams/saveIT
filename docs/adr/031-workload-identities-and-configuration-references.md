# ADR 031: isolated workload identities and pinned configuration references

Accepted for implementation 2026-11-03. Extends ADRs 022, 024, 025, 028–030. This is an unapplied definition, not running ECS, secret population/rotation or managed permission evidence.

Follow-up: [ADR 032](032-private-image-and-log-stores.md) adds optional exact per-workload encrypted-log key permissions/boundaries. Null retains this original bootstrap. Bound web gets only own-log KMS use, with no configuration secrets/query actions; future compute also requires log-key-binding-ready. The original configuration-secret and task/EFS boundaries remain separately enforced.

Create separate task and task-execution roles for API, web, worker, migration and access operations. Trust only ECS tasks from the explicit account/region, with both SourceAccount and SourceArn conditions. AWS currently requires a cluster wildcard in that trust condition; trusted scheduler/PassRole restrictions and actual role isolation remain deployment gates. Task roles carry no general AWS data authority. API alone may receive exact EFS mount/write permission after binding a reviewed filesystem/access point with TLS/mount-target conditions. During bootstrap it explicitly denies all AWS workload actions. Other task roles retain that denial. These are infrastructure identities, never tenant/membership/organization authority.

Each execution role pulls only its designated image repository and writes streams in its own precreated log group. API/worker use their own images; migration/access share the deployment image with separate credentials/roles/log groups. Region-scoped ECR authorization uses the required wildcard resource, while image pulls remain exact-repository. Execution roles cannot assume/pass roles, administer IAM, write secrets, execute SSM sessions or use other AWS actions. Attach explicit-deny permissions boundaries so extra identity/session resource grants cannot widen the declared action/resource/context/version limits. Boundaries are not grants; separate inline policies grant only the required operations. Privileged administrators can still change trust/boundaries and require account-side controls.

Define four separate Secrets Manager configuration containers, each with a rotating protected customer KMS key and thirty-day deletion recovery. Web receives none. A secret is a JSON object whose property names are the exact environment configuration names expected by that process. API includes its connection, Okta client secret, current PFX Base64/password and zero to four contiguous retired pairs. Worker, migration and access contain only their respective connection field. Refer all fields in a workload to one explicit UUID secret version; version IDs are nonsecret metadata and may be chosen before protected population. ECS JSON-key/version selectors, GetSecretValue VersionId conditions and KMS SecretARN/SecretVersionId context keep reads pinned to that reviewed configuration version. IAM authorizes the complete workload secret, not individual JSON fields. The 64 KiB total secret carrier limit can be smaller than combined PFX loader limits; actual payload validation is still required. This is application configuration, not the product vault or tenant credential storage.

Terraform creates metadata/policies only: no secret-version/value resource, secret-value data source, payload/password variable or value output. Existing exact key-administrator and secret-custodian roles remain privileged inputs; custodians need separately reviewed identity permissions and authenticated lifecycle. Secret policies deny unencrypted requests, other readers, unauthorized version/control changes and execution-version mismatch. Key policies constrain service/account/principals, slot-name context and execution version; the slot context uses only the service-generated six-character ARN suffix wildcard until creation resolves the exact ARN. Execution boundaries and secret policies use the resolved exact ARN. No input or output exposes a value. Custodians may manage other versions for a controlled rollout; tasks cannot read them until the pinned definition changes.

Avoid a deployment cycle: first apply workload metadata/roles with no EFS binding, then the key-storage definition using the API role ARN, then reapply the identity root with exact ring IDs. Metadata lookups check filesystem/access-point account/cell/encryption/POSIX/root intent before enabling the API grant. They do not inspect live filesystem permissions, resource-policy drift or perform mounts. Future compute must require the binding-ready output, explicit IAM/TLS volume configuration, protected runtime settings and a platform supporting JSON-key/version injection. ECR/log-group resources, compute/ingress/restricted egress, protected promotion/PassRole/operator execution, live secret population/rotation/recovery and telemetry remain separate work.

Pin Terraform/AWS provider and track signed provider locks/sanitized examples. Test bootstrap/bound plans, exact trust/role/policy/reference relationships, wrong/missing scopes/versions/context, extra-policy explicit-deny intent, maximum retired fields and service policy-size limits with mocks. These are declared-policy and narrow predicate checks, not an IAM simulator or actual AWS enforcement. No account/API use, paid resource or public deployment is needed for tests.

Administration trust is explicit: Secrets Manager UpdateSecret supports metadata maintenance and may also carry a new payload. Key/metadata administrators with its identity permission can therefore replace values directly, as well as alter policies. The custodian restriction on PutSecretValue/version stages is not an exclusive-value-writer guarantee. Authenticated administrator/custodian lifecycle, approvals and change monitoring remain protected deployment controls.
