# ADR 034: private runtime service endpoints

Accepted for implementation 2026-11-03; extends ADRs 028 and 030–033. Define a separate unapplied runtime-endpoints root with ECR API/DKR, CloudWatch Logs and Secrets Manager interface endpoints and a regional S3 gateway endpoint for ECR image layers. Tests use provider mocks, never AWS credentials or apply. This is partial network wiring, not a deployed or runnable cell.

Split the foundation's application route table from its still-local-only database table before associating the S3 gateway. The application table has no inline route ownership so the separate gateway association owns its service route without competing with foundation reconciliation. Validate distinct explicit tables, exact two-subnet associations and account/VPC/cell metadata; reject all routes reported by the pinned provider's data source. That source hides local, gateway-endpoint, propagated, Lattice and some service-ENI routes: an empty list is not a complete route-isolation proof. Direct AWS route/propagation/service inspection remains required. Declared database routes stay local-only, and only the application table receives the new S3 association. No default route, NAT, internet gateway, public IP, IPv6 or peering is introduced. Existing database/NFS standalone rules and ownership remain unchanged.

Create a web client security group with no ingress/database/secret path. Reuse only the three designated API/worker/deployment groups. Each interface endpoint has its own security group; standalone TCP443 pairs admit those four clients for ECR/logs and exclude web for Secrets Manager. Regional S3 prefix-list egress permits only TCP443. Security groups do not filter traffic to the Amazon DNS resolver; DNS firewall/query monitoring and out-of-band drift control remain unfinished.

Endpoint policies are additional filters, never replacements for IAM/resource/KMS policies. ECR permits each exact execution role to authenticate and pull only its own repository (migration/access share deployment); logs permit only own-stream create/put, with no query/control authority; configuration reads require each own exact secret ARN and UUID version. Web has no configuration-read grant. Denies constrain other principals/actions and per-role resources/version. No task-role, scheduler, PassRole, publisher, operator or secret-value authority is added.

ECR layers use the AWS-owned regional starport S3 bucket. The gateway permits only TLS GetObject on that exact bucket's objects with Principal '*', as documented for ECR's presigned layer path; execution-role-only principal filtering would break that service path. It does not grant anonymous access or bypass the object's authorization, restrict layers to our repositories, or support tenant files/backups. Actual allowed/denied service requests, presigned behavior, policy drift, DNS/route/SG isolation and managed ingestion still need isolated AWS verification.

Private endpoints are not restricted Okta egress or an ingress/transport solution. Authenticated encrypted web/API transport, trusted forwarding, database CA delivery, DNS/HTTPS ingress, cluster/services/private launch wiring, protected migration/access jobs/scheduler/PassRole/promotion, telemetry/quotas and operated recovery/fencing remain unfinished. Preserve all enterprise inventory, tenant checks, forced RLS and response-drain authority.
