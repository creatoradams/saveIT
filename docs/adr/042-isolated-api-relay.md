# ADR 042: isolated API relay with protected bootstrap

Accepted for implementation 2026-11-07; extends ADR039–041. This implements a narrow credential-owning relay process and synthetic keyless-web → HTTPS relay → mTLS primary-API path. It is not authenticated web workload identity, cloud secret delivery, a deployed service or launch approval. Exact executed evidence and reviews belong in [progress](../progress.md).

The relay is the API's admitted certificate peer. Any caller able to reach the relay's server-authenticated TLS intake can exercise this delegated transport. That intake does not authenticate the caller as web. API user cookies, CSRF, live membership/organization authority, forced RLS and transactional audit/outbox remain mandatory; no header or relay principal grants tenant authority. Network membership/DNS is not identity. Separate network/process isolation and managed caller/ingress requirements remain pre-launch gates.

Reuse the deployment image, not the privileged deployment service/roles. The Linux-only `serve-api-relay API_HTTPS_ORIGIN RELAY_HTTPS_ORIGIN` command runs before deployment configuration/database initialization. Both public origins use ADR041's canonical ASCII DNS HTTPS authority rules; relay port is fixed8443 and equal origins are refused. Exactly seven protected stdin string fields are accepted: `CertificateBase64`, `CertificatePassword`, `ApiCaSha256`, `ClientLeafSha256`, `ServerCertificateBase64`, `ServerCertificatePassword`, `ServerLeafSha256`. Preserve64KiB original UTF-8/required EOF/ten-second input bounds, duplicate/extra refusal, bounded ephemeral imports and fixed secret-free start/failure output. No private argument/environment/build/Terraform value or secret-manager client is added. Managed input strings are not guaranteed erased.

Load once and retain both owned private leaves and immutable public server roots through host disposal. Require exact public DER pins, eligible current dedicated clientAuth client, current DNS server certificate matching the explicit relay hostname without CN/wildcard fallback, reviewed fixed API-root file/hash and **different RSA public keys** for relay server versus client (SPKI comparison, not merely different certificate DER). This comparison does not prove separation from unrelated API/session keys. There is no reload, rotation or retirement/fencing guarantee. Actual managed PKI/issuance/revocation/intermediate-chain delivery remains unfinished; revocation is NoCheck.

Build an empty explicit Production host without ambient environment/JSON/listener/logging configuration. Clear logging providers before traffic. Serve TLS1.2/1.3 and HTTP1.1 only on8443, with disabled resumption/renegotiation, five-second handshake/header/idle bounds,32 total connections,32KiB request headers and8KiB request target. Literal loopback8080 exposes only exact GET `/health/live`, with no query; remote plaintext/ambient URL listeners are absent. HTTPS GET `/health/ready` actually calls the primary API over mTLS without forwarding cookies. Liveness never substitutes for upstream readiness.

For application traffic accept only GET/HEAD/POST/PUT/PATCH/DELETE below the exact `/api/v1/` boundary. Reject absolute-form targets, ambiguous/encoded path characters, dot/backslash/double-slash paths, malformed percent escapes, fragments/controls, query normalization changes, upgrades, content encoding and trailers. Preserve accepted raw query and opaque body bytes, including OIDC query/form values. Construct target/Host/SNI solely from the fixed startup API authority. This deliberately supports the current REST/OIDC contract, not arbitrary HTTP tunneling, WebSockets, SSE, attachments or a generic gateway.

Allow only Cookie (semicolon semantics), X-CSRF-TOKEN, Accept, Origin, Referer and body Content-Type upstream, subtracting Connection-nominated fields. Drop caller Host, all forwarded/certificate/tenant/service/authentication/tracing headers and hop-by-hop framing. Forward API status, every separate Set-Cookie, Location, Content-Type and Retry-After, with fixed no-store/nosniff; subtract upstream Connection nominations. Preserve redirects for browser/OIDC handling, but never follow them in the relay. No cookie jar, decompression or application retry exists. Outbound requests use exact HTTP1.1/ConnectionClose and a fresh owned ADR041 native custom-trust handler; actual mutual state/exact selected local DER is required before sending HTTP/cookies. Empty native-framed reads skip the large body buffer.

Admit16 active requests with immediate503 and no queue. Hold the slot through response completion/abort. Apply one20-second absolute lifetime, linked to downstream cancellation and host shutdown, plus three-second connect. Completely read/validate request framing/body within1MiB **before** any upstream request, so chunked overflow cannot commit a prefix mutation. Responses stream with backpressure and32MiB cap; current50-revision/50,000-character history pages can exceed15MiB after JSON escaping, so the probe's4KiB cap is inappropriate. Bound upstream headers to32KiB, reject content encoding/trailers, clear owned pooled request/copy buffers and release capacity in finally. Pre-output errors return fixed empty statuses; failures/overflow after output start abort rather than append a second error body. Native internals are not a bespoke one-connection-attempt proof. A failed response never implies a committed mutation rolled back or can be safely replayed.

API OnCompleted still covers API→relay completion only. Relay/Next/browser buffers cannot be recalled by access changes, and no new durable pending-record closure, timeout pruning, force-close, rollback or fencing guarantee is introduced. All existing access drain/epoch/uncertain-commit tests remain required. This relay adds another explicitly bounded buffering hop, without weakening core authority.

The synthetic fixture uses a separate read-only relay container from the same deployment image, only redirected private stdin/public image roots, no DB/operator environment, private fixture/key mounts or shared PID namespace. Ordinary web receives no private material or AWS authority. Primary API now requires the relay client; all four Production identity/access/session/recovery flows must traverse this path, including recovered primary database/key volumes and DB-outage readiness. A separate intentionally reachable server-TLS-only instance preserves TLS controls; this means primary admission is not proof of an exclusive fixture network path. Recovery must stop and verify **all** source API/worker writers before snapshots, and restart that control only after recovered-primary assertions. Owned relay cleanup uses bounded exact-label inspection/removal plus child termination/reap fallback.

Native tests cover target/input/key boundaries, two actual TLS hops, opaque query/form bytes, cookies with Expires commas, preserved redirects/status, header stripping, exact/chunked request limits with zero upstream calls, large history/response overflow/encoding, ordinary server TLS refusal, bad peer/name, POST reset without replay, slow-response deadline,16-slot saturation/caller/host cancellation and capacity reuse. Actual-process packaged checks additionally establish fixed listeners/ambient-config refusal, upstream-backed readiness, anonymous/CSRF refusal, callback-log marker exclusion and positive controls. Local source review and Windows core tests do not establish the Linux serving command; exact Linux execution remains separate evidence.

No Terraform, five-role/secret-selector contract, repository, image count, dependency, schema/OpenAPI, core authorization or146-capability inventory changes are needed. Future relay deployment requires a separately reviewed own identity, pinned protected configuration delivery, public trust/DNS/network/task/service bindings and protected launch/rotation/health/drain/fencing operations. Never assign migration/access-operator roles because the binary shares an image. Edge→web TLS/caller workload admission, actual PKI/IAM/network/RDS/Okta, multi-instance key/recovery and production capacity/SLOs remain unfinished. No account credentials or AWS apply are used for this synthetic slice.

YARP direct forwarding was considered; this narrower existing-contract implementation uses explicit header allowlists and pre-forward request bounds without adding a general proxy dependency.
