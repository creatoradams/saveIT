# ADR 041: bounded outbound API peer probe

Accepted for implementation 2026-11-06; extends ADR039/040. This is a reusable outbound health client and an isolated deployment-tool command, not a web client carrier, forwarding broker, deployed service or production approval. Exact execution and reviews belong in [progress](../progress.md).

The Linux deployment image accepts `probe-api-peer PUBLIC_HTTPS_ORIGIN` with redirected stdin. The origin is explicit trusted operator metadata: canonical ASCII DNS HTTPS authority, optional root slash, no credentials, IP literal, caller path, query or fragment. It is not discovered from a request or inferred from tenant input. Before reading configuration/environment or opening a database, this branch reads exactly four nonempty string fields: `CertificateBase64`, `CertificatePassword`, `ApiCaSha256`, `ClientLeafSha256`. The shared protected-input parser preserves the original 64KiB UTF-8 byte limit, exact case-sensitive fields, duplicate/escaped-alias refusal, depth limit, required EOF and ten-second input deadline. File-path sources and extra fields are refused. Private values travel only over protected redirected stdin, never arguments, environment, Terraform, logs, examples or image layers. The tool emits fixed pass/fail messages without inner exceptions.

The private PFX uses the existing bounded ephemeral importer, exact lowercase SHA256 DER leaf pin and the receiver's shared current RSA2048+/non-CA/DigitalSignature/exclusive clientAuth eligibility check. The deployment image additionally copies the public API-server CA bundle at root-owned mode0444 `/opt/saveit/trust/api-ca.crt`; actual bytes must match the supplied canonical CA-file hash through the existing bounded public-root loader. Default build-context placeholders remain available and deliberately cannot establish trust. No client CA/key is added to web, worker or the public context. Raw input and decoded PFX buffers are cleared; owned certificates/roots are disposed. Managed JSON/password/Base64 strings are not guaranteed to be erased.

A fresh native TLS client uses custom server roots, normal DNS name validation and serverAuth purpose, TLS1.2/1.3, disabled certificate downloads, resumption and renegotiation, and NoCheck revocation. Non-Windows uses an explicitly offline certificate context. Windows core tests use an exact local-certificate selection callback without a competing certificate context: Schannel's anonymous-start bookkeeping otherwise leaves LocalCertificate unset. The CLI remains Linux-only; these Windows tests are not production Windows PFX/TLS support. Immediately after TLS, before HTTP bytes, the handler requires native IsMutuallyAuthenticated plus the exact selected local certificate DER hash. A server-TLS-only200 therefore fails instead of falsely proving client authentication.

The request is exactly HTTP1.1 GET `/health/ready`, without cookies, authorization, ambient proxy, redirects or decompression. Connect timeout is three seconds within a five-second network/response/body deadline. Response headers are limited to4KiB; success requires200, no content encoding and EOF within4KiB, including chunked bodies. It does not interpret the health body or return it. There is no application retry, business request, forwarding API, session authority, database access or secret-manager client. Platform native DNS/connect implementation is not a bespoke guarantee of one network connection attempt.

A pass observes this selected endpoint's native mutual TLS state and bounded successful health response. It does not prove rejection of other credentials, other instances' configuration, expected server-side pin policy, certificate/image association, managed issuance/revocation/rotation, IAM identity, application identity, user/tenant authority or production capacity. Existing membership/organization checks, forced RLS, atomic writes/audit/outbox and response-drain rules are unchanged. No schema, OpenAPI, IAM, secret selector, task definition or dependency changes are needed.

The packaged synthetic fixture passes private bytes only to an isolated read-only deployment container on its known test network; ordinary web still has no credential or new AWS authority. Canaries cover approved/spare peers, server-only TLS refusal, unapproved/foreign/expired/server-purpose credentials, wrong password/pins/CA/name, extra/path/oversized/EOF input and a final positive control. Native tests additionally cover exact/chunked body bounds, stalls/slow drip, status/redirect/encoding and no HTTP bytes before mutual TLS. Shared parser regressions retain late-read cancellation/buffer clearing and existing complete-configuration behavior. Actual Linux packaged execution is required separately from native Windows results.

Next design work must supply the private web/API carrier while preserving web's lack of secret authority and actual-certificate API admission. A same-task sidecar is not an independent IAM boundary: ECS task/execution roles are shared across containers. No broker is introduced here. Client delivery, constrained forwarding/trusted headers, ingress/services/registration/health/drain, protected operations, managed PKI/IAM/RDS/Okta verification and operated fencing/recovery remain unfinished. No account credentials or cloud apply are required for this precursor.
