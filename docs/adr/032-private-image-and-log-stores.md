# ADR 032: private image repositories and bounded operational log stores

Accepted for implementation 2026-11-03; extends ADRs 004, 026–028 and 031. These are unapplied resource definitions, not published images, collected logs, protected promotion or running ECS.

Add a separate `artifact-stores` Terraform root with four private ECR repositories (`api`, `web`, `worker`, `deployment`) and five CloudWatch log groups (`api`, `web`, `worker`, `migration`, `access`). Names/ARNs must match the existing workload-identity root; migration/access share the deployment image but retain separate roles and logs. Native cross-root plan assertions check that contract. All inputs are nonsecret metadata; no value/version lookup or payload enters Terraform. Workload roles remain infrastructure identities, never tenant authority.

Repository tags are immutable without exclusions, force-delete is false and Terraform prevents destruction. No automatic lifecycle/expiry rule is created: untagged images, rollback candidates and future attached signature/SBOM artifacts must not be silently expired. Repository policies explicitly deny insecure requests, pulls outside the designated execution roles/publisher/administrators, pushes outside the single publisher, image deletion, and control changes outside trusted administrators. They grant no identity permissions; the future protected publisher still needs reviewed exact identity permissions and regional registry authorization. Root/key administrators can alter policies and remain trusted; these controls are not tamper proof or proof of authenticated promotion. Pull-through/replication/Lambda consumers and cross-account access are not configured.

Use one rotating protected customer KMS key for this cell's four image stores, constrained to regional ECR, caller account and the four exact repository encryption contexts. ECR-managed service grants are required; deny arbitrary non-resource grant creation. The actual infrastructure identity must have the documented create/describe/retire-grant permissions, with RetireGrant in its identity policy. Encryption settings are chosen before creation and cannot be changed in place. Repository basic scan-on-push is enabled as supplemental configuration, never a substitute for the existing same-image CI vulnerability gate or actual managed scanning evidence. Account registry-wide scan settings are not owned here.

Each operational log group has its own rotating protected KMS key, exact log-group encryption context, regional Logs service allow, and a nonadministrator data-use boundary admitting only that service principal or regional Logs forwarding. Protect log groups from deletion and pin STANDARD class with explicit finite retention (default 90 days, supported choices 30–365). This is a configurable operational default, not an approved legal/audit retention requirement. Retention expiry still deletes events; this is not immutable audit storage, recovery or a compliance archive. Root/key administrators can change retention/key/policies and remain privileged.

AWS's encrypted PutLogEvents caller path also needs KMS authority. Extend workload-identity with an optional distinct five-key `operational_log_keys` binding using these exact output key ARNs. Null retains the original unbound bootstrap. Bound execution roles gain only their own log key's crypto through regional Logs with the exact group context; DescribeKey is separate, exact-key and via Logs without an unavailable encryption context. Full explicit-deny boundaries constrain other actions/keys/direct/wrong-context requests and keep configuration-secret decryption pinned separately. No configuration key can be reused as a log key. Web gets own-log KMS authority but no secrets or log-query actions; task-role boundaries remain unchanged. Future encrypted compute must require both log-key-binding-ready and EFS-binding-ready. Input validation/cross-root plans check declared references, not live key-policy drift or successful ingestion.

Provider mocks cover resource/settings/wiring, full policy shapes, missing/wrong principal/service/account/context predicates, publisher/admin/workload separation, accepted limits and the real alternate-module reference contract. They do not evaluate IAM or prove AWS service grant behavior. Track provider locks/sanitized examples; keep state, plans, local values and test evidence ignored. No AWS APIs, account credentials, paid resources or apply are needed for tests. Registry publishing/signing/protected promotion, ECS task/services, network/ingress/egress, redaction/collection/alerts/quotas, managed authorization/retention/recovery and live identity remain unfinished.
