# ADR 006: rebuildable local full-text search and a restricted outbox consumer

Accepted for the second local slice, 2026-10-28; queue discovery updated 2026-10-29 under [ADR 011](011-transactional-search-queue.md). Schema-v1 Organization.Created/Revised are also explicit metadata-only acknowledgments under ADR 012; current organization labels are read from core authority and worker EXECUTE on administration functions is forbidden. OpenSearch remains the enterprise target; it is not implemented by this decision.

## Choice and tradeoffs

Use a **derived PostgreSQL full-text projection** for the current small local deployment. This reuses the real database already required by the application, keeps the one-command development path, and lets us test durable delivery and authorization boundaries without adding an unoperated search service. This is a deliberate first search implementation, not an OpenSearch mock. Move to OpenSearch behind the candidate-retrieval boundary when measured corpus/relevance/independent-scaling requirements justify it. Do not claim distributed search resilience or enterprise search parity.

`services/search` owns projection processing, receipts and query SQL. `services/workers` runs its actual background consumer. Core exposes `CoreSearchSources`, a PostgreSQL **security-invoker** read view over current asset/document records; underlying RLS applies to the caller. Schema migrations remain coordinated in the API. The worker cannot mutate core records, outbox events, grants or audit. It has its own non-owner, NOBYPASSRLS role, explicit configured tenant allowlist, and transaction-local tenant context. It can write only search projections and this consumer's receipts. No user-controlled request schedules a different tenant.

PostgreSQL `tsvector`/GIN and `plainto_tsquery` implement complete-word, AND-term matching with per-document ranking. The `simple` configuration preserves technical words rather than treating IT vocabulary as English stop words. Search has at most 12 terms / 120 characters, 25 authorized results per page, scope/type filters and query/principal-bound cursors. There is no typo tolerance, prefix autocomplete, facets, total count, file/credential search or advanced query language. See [PostgreSQL text search](https://www.postgresql.org/docs/18/textsearch-controls.html) and [Npgsql mapping](https://www.npgsql.org/efcore/mapping/full-text-search.html), checked 2026-10-28.

## Authority and disclosure

An index hit never grants access. The search statement joins current active membership, organization grant, organization, and current core source. It requires exact tenant/organization/asset/type/version/title/body agreement with the projection. This excludes stale candidates, including a removed word in an older revision, until the new projection catches up. Titles, organization labels and bounded plain-text previews come from current core rows. Ranking uses individual authorized documents, not cross-tenant corpus statistics. Apply authority checks **before** pagination; no unauthorized hit counts or continuation hints are exposed. Search terms and body previews are never stored in audit/outbox/log messages.

Every returned asset/document result creates a read audit in the request transaction. If authoritative SQL or auditing fails, no results/cursor are serialized; projection failure returns 503 without cached/direct-query fallback. The UI clears results on scope changes or failures, and normal authorized endpoints recheck a result again when opened. Previews render as React text, never HTML.

READ COMMITTED statement snapshots and existing in-flight-request revocation semantics remain as specified in ADR 002. No permission-administration endpoint or synchronous revocation barrier is introduced. Index lag cannot grant access on a later request, but already delivered content cannot be recalled.

## Delivery and recovery

Outbox rows stay immutable invalidation metadata. `SearchDeliveries` owns search-v1 pending/completion/attempt state; legacy `OutboxEvents.DeliveredAt` remains untouched so a search receipt cannot imply delivery to future consumers. A fixed restricted trigger enqueues pending work atomically with every outbox insert. Due selection uses the pending partial index, with no timestamp checkpoint or scan through completed history. Enqueue failure rolls back the core transaction; see ADR 011 for ownership/production prerequisites. For each configured tenant, a transaction-scoped advisory lock serializes consumers/rebuilds; another worker skips busy tenants. Each bounded batch processes at most 100 due events. Asset.Created/Revised/Restored and Document.Created/Revised/Restored schema-v1 events rehydrate the **latest** source. Missing source removes that target's projection. Schema-v1 AssetRelationship.Created/Removed, Location.Created/Revised and Contact.Created/Revised events are acknowledged without projection changes; relationships/directory fields are not searchable. A scoped source mismatch or unknown type/schema becomes a dead letter. No cross-module write or event payload content is trusted as source data.

Projection mutation and successful receipt commit in the **same transaction**. A duplicate acknowledged event is skipped; replay of an older invalidation rehydrates current state. Version-guarded upserts prevent regression. This provides local transactional effects, not exactly-once claims about future external APIs. On a database failure, roll back the projection and persist a safe error code/attempt in a separate tenant transaction. Retry after exponential backoff plus jitter (up to 60 seconds, five attempts), then dead-letter. If the database cannot record failure, leave the event pending and retry after recovery. Cancellation/crash before commit leaves no successful receipt.

`npm run search:rebuild` atomically rebuilds each configured tenant from current sources, without changing core data or other tenants. New writes still emit invalidations and catch up afterward. `npm run search:once` drains one bounded batch per configured tenant. To retry a known failed event after fixing its cause, run `node scripts/search-worker.mjs --replay-event <event-uuid> --once`; this resets only the matching consumer receipt inside the configured tenant boundary. Rebuilds and consumers use the same lock. The local launcher rebuilds on startup and then polls once per second. Large-tenant chunked rebuilds, dead-letter administration UI, signed/immutable operator audit and production scheduling remain backlog items.

To inspect failures with the restricted worker role, set the configured tenant transaction context, then query `SearchDeliveries` for `DeadLetteredAt IS NOT NULL` or incomplete attempts; record event UUID, attempts and ErrorCode, never document content. Replay resets an existing scoped receipt; wrong-tenant/missing receipt returns false. The worker has no DELETE privilege on receipts. Do not delete receipts or mark global DeliveredAt manually. Replay is a trusted operator command, not a public permission-administration API.

## Acceptance evidence and limits

Real-PostgreSQL tests cover stale index content, committed revocation with an unchanged projection/cookie, two-tenant and organization filters, cursor scope/limits, unavailable projections, audit failure, duplicate/reordered/concurrent delivery, transactional receipt failure, retry/dead-letter/replay, tenant-scoped rebuild/missing-source cleanup, unsafe-role rejection and actual worker/app privileges. Browser tests exercise actual worker indexing, current-document navigation, tenant separation, escaped previews, outage recovery, context reset, axe and responsive layout. No load/SLO, production recovery, immutable archive, OpenSearch or vendor parity evidence is claimed.
