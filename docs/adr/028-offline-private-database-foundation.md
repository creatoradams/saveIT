# ADR 028: isolated network and managed-database foundation

Extension 2026-11-03: ADR 034 separates application and database route tables before the separate runtime-endpoints root adds application-only S3 image-layer routing. Database routes and existing database/NFS rule ownership remain unchanged. Both roots remain unapplied; the original foundation-only scope below is historical.

Accepted for implementation 2026-11-02. Extends ADRs 004/022/024. This is a separate unapplied root, not a deployed or complete application cell. Only mocked provider plans are executed without AWS credentials/API calls. Progress records actual checks.

Require explicit commercial account/region, cell/environment, two distinct actual AZs, a reviewed nonoverlapping canonical private /16, bounded key-administration roles and explicit PostgreSQL 18 major-prefix/class/storage intent. Pin the same AWS 6.71.0 provider and signed Linux/Windows hashes. Do not infer an account from ambient credentials or default region/budget/residency. Mocks cannot prove region/class/engine availability; verify actual orderability before an authorized plan/apply.

Define one DNS-enabled private VPC, two application and two disjoint database subnets, a local-only route table and an empty default security group. There is no internet gateway, NAT, public IP, load balancer, VPN, peering, endpoint or compute. Three distinct future API/worker/deployment groups have only declared TCP 5432 paths to the private database group. No web group receives database access. Use standalone rules to avoid cyclic/mixed-inline rule management; the provider removes AWS's default outbound rule at creation. These definitions do not police privileged out-of-band rule additions: account-side drift/audit enforcement and actual reachability tests remain required.

RDS PostgreSQL storage and backups use a rotating customer-managed key with a thirty-day deletion window. Key policy explicitly denies nonadministrative control-plane changes, non-RDS cryptography and arbitrary grants. Exact key administrators and account-root recovery remain privileged, including the account IAM-delegation boundary; policy mocks are not an IAM simulator or actual KMS-service proof. Test managed-service grants/backup/failover/recovery with the actual roles before release.

RDS generates/manages the separate bootstrap master password in Secrets Manager, using that service's managed encryption key. Do not add a password input, secret version/value resource/data lookup, or credential output. Terraform holds resource metadata/identifiers and still needs protected remote state, not secret values. The bootstrap login is neither the application nor worker login. Existing restricted roles/functions, forced RLS, TLS/namespace/schema/startup guards, migrations, provisioning and access-response drain must still be verified on the actual managed service; no master connection may become runtime authority.

Define private IPv4 access, SSL enforcement, restricted statement/error logging, 35-day automated backup intent, retained automated backups, final-snapshot/deletion protection and Terraform prevent-destroy boundaries. Production intent enforces multi-AZ and a storage floor; staging is single-instance and has no availability claim. Automatic minor servicing is enabled, major upgrades and immediate apply are disabled. Snapshot naming/destruction and service maintenance require explicit review. Parameters/backups do not establish redaction, immutable/offsite backup, managed restoration or measured SLO/RPO/RTO.

The root deliberately has no default remote backend. Before any authorized real apply, configure the existing bootstrap's protected named cell state key and verify locking/account/key access. No state/plan/backend credentials are committed. Infrastructure execution must use short-lived federated roles, explicit budget/residency and reviewed plans. Application compute/ingress/restricted egress, registry/signing/promotion, runtime secrets/key persistence, private operator reach/fencing, actual managed role/CA/restore evidence, telemetry/quotas and operating controls remain unfinished account-free/environment work. No AWS account, resource or public deployment is created by this definition.

Primary guidance: pinned [RDS resource](https://github.com/hashicorp/terraform-provider-aws/blob/v6.71.0/website/docs/r/db_instance.html.markdown), [security-group default/rule behavior](https://github.com/hashicorp/terraform-provider-aws/blob/v6.71.0/website/docs/r/security_group.html.markdown) and [RDS-managed master credentials](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-secrets-manager.html).

Sort AZ names before assigning stable CIDR slots. Use PostgreSQL 18 major-prefix selection with automatic minor servicing, not an exact minor that could become an unsupported downgrade request after service maintenance; expose/verify the actual minor separately. Both choices have mocked regressions. AWS specifically [warns about internal resource-owning-account access under blanket KMS denies](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Overview.Encryption.Keys.html). Actual managed service-linked grant/backup/maintenance/failover/key-recovery behavior is a mandatory pre-deployment gate; mocks do not resolve it, and this definition adds no blanket same-account exemption.
