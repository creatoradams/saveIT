# ADR 012: limited organization administration and paged selection

Accepted for the local core, 2026-10-29. Supplements ADRs 001/002 and retains the complete enterprise roadmap.

Organization creation requires a current active membership with a separately provisioned CanManageOrganizations capability. Renaming also requires an existing current Editor grant for that organization. This flag is not a cookie/provider role, and does not reveal unassigned organizations or grant access to existing records. Session metadata exposes it for presentation; every protected request reads it from PostgreSQL again. The runtime cannot update membership flags or directly insert/update organizations/grants.

Two fixed database functions perform the narrow writes. Creation uses a server-generated UUID and plain INSERTs for a brand-new organization and its creator's initial Editor grant. Reusing an existing organization must fail; there is no UPSERT, enrollment by email or arbitrary target membership. Rename changes only name/version/time after an expected-version predicate. Both functions validate the transaction-local tenant and membership, explicitly qualify every elevated lookup by tenant, and share-lock the current active administrator membership; rename also locks its Editor grant. Missing authority fails closed; concurrent/stale versions return 409.

The functions are SECURITY DEFINER with qualified public tables, fixed pg_catalog,pg_temp search path, no dynamic SQL, no PUBLIC execution and API-only EXECUTE grants. They share TenantFilter's outer transaction with successful audit/outbox/pending search receipts. Audit/outbox/queue failure rolls back the organization and initial grant or rename. Runtime direct INSERT/UPDATE stays denied. Automatic approval review rejected the initial column-UPDATE grant as too broad; checked rename replaced that proposal. This is a narrower implementation, not an override of that rejection.

The search worker treats execution of either function as a core-write capability. Startup rejects direct, PUBLIC or reachable NOINHERIT role EXECUTE, in addition to existing owner/BYPASSRLS/core table/column checks. Organization.Created/Revised schema-v1 events receive metadata-only acknowledgments; names are supplied by current authoritative organization rows during search, with no organization-label projection or new permission source.

The local migration adds default-false capability and version/time columns. Synthetic development seeding provisions Alice and Bob and restores that capability on explicit local seed/startup; Sam remains a Viewer. Production does not run development seed. Real administrators must be provisioned by a separately controlled process, and production function ownership/forced-RLS/tenant-context/backfill operations require review as in ADR 011. No live Okta/admin lifecycle or cloud deployment is established.

## Pagination and API compatibility

The local v1 GET /organizations response changes from a capped array to `{ items, nextCursor }`, with at most 50 currently granted organizations. All repository callers and generated schemas are migrated together. There is no deployed external API compatibility claim. Ordering is database name plus UUID; duplicate names use UUID tie-breaking and an index on TenantId/Name/Id. Cursors are Data Protection-protected, bounded, and bound to the current tenant and membership. Every page rechecks current grants before names or continuation are returned; read audits commit before serialization.

GET /organizations/{id} provides audited current name/role/version lookup for an authorized ID. Search navigation uses this endpoint to open an organization beyond the loaded picker page and obtain current role/name before switching context. Picker pages merge by ID and expose explicit load-more controls. Pages use READ COMMITTED snapshots; concurrent renames/grant changes can reorder a collection, so restart pagination when an up-to-date complete listing is needed. No snapshot inventory or inaccessible total count is exposed.

The browser provides create/rename, explicit conflict/reload, preserved unsaved text after a failed reload, current role labels and accessible native controls. A create grants its creator only; other memberships require the existing controlled provisioning process. No organization archive/delete, arbitrary grant editing, capability administration or permission-revocation API is introduced. Therefore this slice does not establish a generalized revocation barrier. Existing request snapshot/in-flight limits in ADR 002 continue to apply.

Evidence: OrganizationTests covers persistence, capability/Editor/revocation/CSRF denial, function/table permissions, expected-version races, audit/outbox/queue rollback, more than 100 records with duplicate names, principal/tenant-bound cursors, fail-closed read audit and worker EXECUTE rejection. Browser evidence covers create/conflict/recovery, pagination and beyond-page search navigation. Verification and review outcomes are recorded in progress, not inferred from source alone.
