# ADR 035: packaged API server TLS and public web trust

Accepted for implementation 2026-11-04; extends ADRs 022, 029 and 033–034. This is an account-free packaged transport slice, not deployed workload authentication, managed PKI or production approval. Execution evidence belongs in progress.

Add an explicitly enabled Linux `Deployment:ApiTls` mode. Choose exactly one `CertificatePath` or `CertificateBase64` PFX source plus its protected `CertificatePassword`. Reuse the bounded, same-open-file, ephemeral RSA import and owned-buffer clearing implementation from the session-protector loader, wrapping all failures in a transport-specific sanitized message. Transport credentials must use a separate key from the persisted session-key protector. Require a currently valid RSA private key of at least 2048 bits, explicit server-auth EKU, non-CA leaf and exactly one parsed SAN extension with usable DNS names. Empty, malformed or URI-only SAN cannot fall back to CN. This slice supports DNS server identities, not IP-only certificates. The current loader returns a leaf: intermediate-chain delivery, revocation, issuance, renewal and rotation require further implementation and managed proof.

Enabled mode has fixed IPv4 HTTPS8443 (TLS1.2/1.3) and literal IPv4 loopback HTTP8080. Replace the reloadable Kestrel endpoint source and reject Kestrel configuration and configured forwarded peers/networks. Code listeners override URL/port shorthands; packaged tests deliberately supply a conflicting URL. Before routing, authentication or response registration, require the actual TLS connection feature, except exact loopback8080 GET `/health/live` and `/health/ready`. Neither a scheme string nor forwarded metadata authorizes plaintext API access. Forwarded processing is unconfigured/disabled in this mode; native TLS supplies the secure scheme. Preserve the bounded direct-loopback health CLI. Linux serving is intentional: Windows Schannel cannot serve ephemeral imported PFX keys. Local Windows tests import only their own synthetic fixture through the temporary default key store for handshake diagnosis; Linux CI serves the actual application loader.

The default local Development HTTP workflow remains. The API mode is opt-in and is not a universal Production TLS assertion; Production web now refuses HTTP API origins and `NODE_TLS_REJECT_UNAUTHORIZED=0`. The packaged Production fixture enables API TLS and gives web only its public CA file through startup `NODE_EXTRA_CA_CERTS`. Do not mount private API/session keys or add secret authority to web. Readiness requires exact HTTP200 and refuses redirects. Retain Next's native rewrite streaming, cookie, redirect and cancellation behavior; no new tenant or workload authorization derives from TLS or headers.

Pinned Next's proxy error diagnostic includes its full target query, potentially containing OIDC callback codes. The packaged `runtime.cjs` entry point replaces only the exact `Failed to proxy ` console diagnostic with a fixed value before loading Next. This is a narrow pinned-framework redaction contract, not general log collection/redaction. Actual packaged tests send marker callback queries through failed CA/hostname/expired-certificate rewrites, require a new sanitized diagnostic for each callback and inspect output only after bounded shutdown/stdio drain. Keep that canary on dependency changes. Other operational telemetry/redaction remains unfinished.

The unapplied task root now declares HTTPS8443 and enabled API TLS, keeping its loopback readiness command. Its existing exact configuration selectors intentionally do not yet deliver a transport PFX, private CA bundle or RDS CA file: task startup remains blocked until a separately reviewed metadata-only delivery contract is implemented. Do not populate payloads in Terraform or imply this task definition can launch successfully. No roles, secret-read permissions, endpoint filters, tenant authority or core database behavior are broadened.

Packaged canaries cover trusted CA/name, untrusted CA, wrong name, expired leaf, refused HTTP origin, refused TLS-validation bypass, readiness/rewrite redirect refusal and no remote8080/URL-override9999 listener. The isolated test runner alone mounts a synthetic TLS-server key to serve redirect/expiry fixtures; the ordinary web service mounts only the public CA. Checks have absolute request/body/startup/log/shutdown deadlines and bounded content-free output. Existing synthetic OIDC, session replacement, retained-key/database recovery, live authorization and database-outage health flows must still pass. These are root-signed synthetic fixtures, not real Okta, intermediate PKI, AWS IAM, mTLS or managed recovery evidence.

Before launch: finish certificate/CA delivery and lifecycle, authenticated workload/ingress transport, service DNS/discovery and network paths, restricted Okta egress, protected services/jobs/promotion/PassRole, redacted telemetry/quotas and operated fencing/recovery. The edge-to-web synthetic HTTP hop is separate unfinished ingress work. Preserve all enterprise capabilities and every current tenant/RLS/audit/response-completion boundary.
