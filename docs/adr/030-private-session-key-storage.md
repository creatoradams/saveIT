# ADR 030: isolated persistent session-key storage definition

Accepted for implementation 2026-11-02. Extends ADRs 022, 023, 028 and 029. This is an unapplied storage definition, not a running application cell or managed recovery proof.

Add a separate Terraform root for a regional EFS filesystem dedicated to one cell/environment's encrypted Data Protection key ring. API replicas need the same persisted ring and protector set; worker, web and migration tasks do not. Separate state/lifecycle protects storage from routine compute replacement. The existing PFX encryption remains required in addition to storage encryption. Never use this filesystem as a general vault, upload volume or tenant authority.

Require explicit authorized account/region/cell/environment, actual foundation VPC/two private application subnets/API security group, exact API task-role ARN and separate key administrators. Provider lookups check VPC/private-address configuration and distinct AZ placement. Define two private mount targets, API-group-only TCP 2049 ingress/egress, a rotating protected KMS file-data key, enabled automatic backup enrollment and a nonroot access point with a 0700 dedicated directory. Filesystem policy denies anonymous/other roles, absent/wrong access points, insecure mounts and client root access; only the API task role receives mount/write through that access point with TLS/mount-target conditions. Task metadata explicitly requires IAM authorization and transit encryption; compute wiring is separate unfinished work.

KMS data use is limited to EFS in the designated account/region, with explicit non-EFS/grant/control-plane deny boundaries and privileged exact key-administrator/account recovery exceptions. These administrators can change policy and remain a trusted boundary. EFS encrypts file contents with this customer key and metadata with its service-managed key. No PFX, connection string, secret version or secret value enters Terraform. The runtime role is not a key administrator and receives no direct KMS policy grant here.

Mock plans verify declarations and negative input/lookup cases without AWS calls. They are not an IAM evaluator or proof of EFS/KMS service grants, mounts, throughput, backups, restore, multi-instance key creation or session continuity. Automatic backup enrollment is not a reviewed retention/vault/restore design. Actual task/secret-reference wiring, cost/capacity review, protected backup/retention/fencing procedures, managed restore/key lifecycle and live identity still require completion and evidence. No account or paid resource is created by this change.

Guidance: [ECS/EFS security controls and IAM mounts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/efs-best-practices.html), [EFS KMS permissions and key lifecycle](https://docs.aws.amazon.com/efs/latest/ug/EFSKMS.html) and [ECS access-point authorization configuration](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_EFSAuthorizationConfig.html).
