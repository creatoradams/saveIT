# ADR 029: bounded injected session-key protector configuration

Accepted for implementation 2026-11-02. Extends ADRs 010/022/023. This is configuration support for protected deployment injection, not a working secret-manager integration, automatic rotation, vault or managed recovery claim. Execution evidence belongs in progress.

Production Data Protection still requires an explicit persisted, certificate-protected key ring. Each current or retired protector chooses exactly one protected PFX path or Base64 PFX value. `Identity:KeyCertificateBase64` supports task secret injection without writing a plaintext PFX to a container filesystem; a configured file remains supported. The password is separately protected configuration. Retired entries accept `Path` or `Base64` plus `Password`, bounded to four as before. Both sources together, neither, oversized/invalid data, missing/unsupported/weak private keys and invalid current validity fail startup. This is privileged server configuration and never request/tenant authority.

Bound decoded PFX input to 64 KiB (and encoded/path input lengths), inspect/read a single open file with a growth cap, import RSA private keys of at least 2048 bits using EphemeralKeySet and zero owned decoded buffers after import/failure. Current protectors must be presently valid. Retired RSA private certificates may be expired for controlled decryption continuity; they are not used for new encryption. Sanitize parser/filesystem/crypto exceptions without reflecting values/passwords. Ephemeral import avoids an additional OS persisted private-key copy; the native key must remain usable in process memory. Managed configuration/environment strings are not erased, and secret-store/environment carrier limits may be smaller than the loader's maximum. Never dump configuration, environment or private certificates into logs/arguments/artifacts.

Preserve existing session-cookie/epoch checks, key-ring/application identity, encrypted persistence and prior-certificate unprotect behavior. No provider identity, tenant mapping, roles, RLS or access drain changes. Synthetic tests load both formats, reject unsupported sources and keys, and actually encrypt/reload a persisted key ring under replacement/current+retired protectors. Packaged CI must switch a running synthetic API from file to injected current/prior values after replacement, verify the old cookie and retained records, then retain isolated recovery/file-mode checks. Generated synthetic configuration stays ignored with private file permissions; it is not committed.

Actual secret-manager reference IAM/KMS controls, runtime key storage/multi-instance mounting, provisioning, live Okta/MFA, key creation/rotation/retirement ownership, backups/fencing/managed recovery and independent assurance remain deployment gates. No cloud account, real secret, purchase or public deployment is introduced.

Primary guidance: [explicit Data Protection encryption at rest](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-encryption-at-rest?view=aspnetcore-10.0) and [ephemeral PFX import semantics](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.x509certificates.x509keystorageflags?view=net-10.0).
