# ADR 022: separate deployment authority and packaged Production-mode verification

Accepted for implementation 2026-11-01. Extends ADRs 001/004/010. Verification status is recorded in progress; accepted design is not evidence of a cloud deployment or production approval.

Production deployment uses a separate `SaveIT.Deployment` console process. The API retains only the explicit Development migration/seed command; that command remains impossible in Production. The deployment executable has no synthetic seed/default connection, accepts protected connection configuration and bounded private provisioning files, and prints generic completion/failure messages without provider exceptions, SQL or identities. Its forward-only migration path rejects ahead/divergent schema histories and serializes deployment/provisioning under a dedicated session advisory lock. Nonpooled physical connection disposal releases the lock on success/failure. Provisioning is insert-only and requires the exact complete release history; retry cannot update existing authority.

An authorized administrator first creates fixed nonprivileged roles and an empty database owned by `saveit_migration_owner`. That non-login owner has no superuser/BYPASSRLS/CREATEDB/CREATEROLE/replication attributes. Only a separate deployment login may reach it; runtime roles must never do so. Historical migrations and grants are preserved. The deployment session fixes the public namespace and installs an owner-only permissive RLS policy on each existing RLS table before upgrades and after each migration. This allows later all-tenant backfills and narrowly checked definer functions to work without superuser/RLS bypass. Runtime tenant policies and forced RLS remain intact. New historical tables backfill before enabling RLS. Future migration designs must preserve that ordering or explicitly install their owner policy before protected backfill; the existing two-tenant upgrade test is a regression baseline. Managed PostgreSQL bootstrap/role/function behavior still needs actual staging evidence.

Initial provisioning atomically inserts the explicit tenant and mapped active administrator membership, calls the existing checked organization-creation function (including actor-bound history and creator grant), and appends `Tenant.Provisioned` audit plus known schema-v1 organization invalidation/queue. Names/identity subjects do not enter outbox or audit metadata. The declared operator is attribution from a privileged operator, not a cryptographic identity attestation. General member/grant editing, offboarding, in-flight revocation and multi-connection enterprise identity remain separate work.

Runtime startup guards now reject schema CREATE reachable through direct/PUBLIC/NOINHERIT roles as well as owner/elevated-role reachability. API, worker and deployment connections fix `search_path=public` and reject arbitrary startup options. Outside Development, database TLS must verify certificate/hostname; the explicit test escape accepts only literal loopback/localhost and cannot authorize remote plaintext. Production API startup and all worker execution paths require the release migration marker and all 25 forced-RLS tables. Runtime roles receive only the history marker column for schema checks. Public liveness/readiness output contains no schema, role, identity or connection details. Readiness is not authorization.

Trusted proxy processing handles only forwarded protocol, before authentication/CSRF. It trusts configured bounded IP/CIDR entries, refuses global wildcards and disables forwarded-header processing when unconfigured. Other sources cannot make an HTTP request satisfy secure-cookie CSRF requirements. The web proxy validates the configured public Host and reads API/issuer/public origins at runtime, with no credentialed frontend variables. Protected responses are no-store. Dynamic rendering supplies a fresh nonce to framework scripts; production script CSP permits neither unsafe-inline nor unsafe-eval. Style inline support remains an explicit limitation. Health-only routing tolerates load-balancer Host probes without granting data access.

Pinned multi-stage images run web/API/worker/deployment as nonroot. Application image targets do not include the separate test identity process. Linux CI is responsible for actual image execution because the local Windows Docker Linux engine is unavailable. The synthetic test graph uses TLS ingress/provider and certificate-verified database TLS, a distinct real OIDC process with code/state/nonce/PKCE validation, two provisioned synthetic tenant/org scopes, protected persisted session keys, immutable images and readonly runtime filesystems. Browser certificate errors are ignored only for the fixture; curl verifies the generated CA. Passing this test is not live Okta or managed-cloud evidence.

Worker probes report successful committed progress rather than waiting for a complete bounded tenant list. Production work units have a 20-second cancellation deadline; connection/command waits are capped at five seconds and cancellation acknowledgement at two seconds (including explicitly infinite input settings; immediate cancellation remains supported). A selected event exceeding its unit deadline rolls back and records ordinary bounded retry/backoff/dead-letter under a fresh five-second cleanup token and separate validated connection. Host shutdown does not invent a failure attempt. A broken original session resumes on the next batch. The probe expires after 60 seconds without progress. Tenant failures keep readiness false until that tenant succeeds, and schema failure prevents processing. Queue lag/dead-letter/delivery SLO monitoring remains separate operational work.

Prior key-protection certificates can be retained through a bounded retirement list to decrypt existing rings after protector replacement. The packaged restart/old-cookie test checks that recovery path; it does not prove a new Data Protection key was generated under the replacement protector, automated rotation, key backup recovery or live operator key controls. Real environment key separation, certificate protection/rotation and recovery drills remain release gates. No production readiness or enterprise completion is implied.
