# Bounded local API load measurements

The local harness exercises the real Development API and PostgreSQL through separate Alice/Bob synthetic sessions. It is a reproducible client probe, not a production capacity test, quota implementation or service-SLO gate. No application contract, authorization, RLS or audit behavior is replaced.

Start `npm run dev`, wait for readiness and finish any browser/regression run before measuring:

```powershell
npm run test:load-harness
npm run load:local -- --allow-local --requests 240 --concurrency 8
```

Use only the known synthetic stack started from this repository. The CLI requires explicit `--allow-local`, an HTTP `127.0.0.1` API origin (default port 5080), enabled synthetic development adapter with Okta disabled and the exact two synthetic tenant sessions. It refuses remote/HTTPS/userinfo/path/query/fragment origins and redirects. A scoped `node:http` agent with an empty proxy environment bypasses ambient Node proxy settings; a child-process proxy canary verifies zero proxy connections under `NODE_USE_ENV_PROXY=1`. Loopback transport does not attest that a local listener is not itself a port-forward/proxy or that all stored data is synthetic. `--base-url http://127.0.0.1:5081` supports another local API port. Counts are canonical integers bounded to 6–1,000 measured requests and 1–16 in-flight requests shared over two cookie sessions. This is a closed-loop request probe, not that many independent users or a controlled arrival-rate workload. Total setup/workload deadline is 120 seconds; each response has a five-second deadline and 256 KiB body limit, and encoded responses are rejected. Failures emit a fixed generic error without response/exception/cookie/configuration details.

Setup signs in each profile, verifies its expected synthetic tenant and checks a fixed foreign organization's asset page returns 404. It then warms one organization-list, scoped asset-list and scoped `switch` search page per tenant. The measured workload alternates the two tenant sessions and cycles those three paths (six fixed groups). Page bounds and scoped asset/search organization IDs are checked. Organization lists reject the known foreign fixture organization and validate ID-string shape; DTO-only checking does not establish ownership of arbitrary organization IDs. This probe's fixed preflight/shape checks complement the real isolation tests; they are not comprehensive authorization verification. Normal sign-in, response-registration/completion and required read-audit writes occur. Business records are not mutated by the probe. Repeated runs add normal audit/protocol traffic; use only retained/disposable synthetic development data.

Reports are written exclusively to ignored `.local/load/<timestamp>-<random>.json`, with a private file mode where supported. Output contains only bounded timing/status/count/workload/client metadata, observed first-page counts, validated-response item totals/minimum/maximum per group and repository start/end checkpoints. It retains no bodies, names, record IDs, cookies or tokens. Repository checkpoints identify the checkout, not the loaded API binary or absence of edits between checkpoints. Do not commit reports. The eight tool tests use real local HTTP fixtures for opt-in/count bounds, percentile correctness, nondevelopment/oversize refusal, redirect refusal, stalled-body deadline enforcement, separate cookie jars/concurrency, content-free summaries, known foreign-list refusal and proxy-mode bypass. The proxy canary first proves global fetch reaches the configured proxy, then verifies the probe makes zero proxy connections. These fixtures do not replace PostgreSQL application tests.

Latency uses monotonic client time through full response consumption, JSON validation and source-shape checking; nearest-rank p50/p95/p99/max include failed attempts. Throughput divides completed measured attempts by measured wall time, including validation/scheduling. Setup/warm-ups are excluded and counted separately. Durable API completion callbacks can finish after the client receives the body, so this does not measure their acknowledgement latency or prove pending protocol state is clear. HTTP/shape failures and incomplete budgets exit nonzero; no latency target is silently treated as achieved.

First local experiment on 2026-11-02 used 240 requests/concurrency 8, two retained synthetic tenants, Windows x64, local Node 24.16.0 client, 32 logical CPUs and about 32 GiB memory. All 240 returned valid 200 pages; p50 9.77 ms, p95 49.05 ms, p99 390.36 ms and maximum 597.75 ms. The checkout was modified, with start/end repository revision 194c506, and API ran the retained development stack. A single warm-up/path does not control caches/JIT or establish steady-state results; dataset total size was not measured. These numbers are an initial debugging baseline, not comparison to the proposed production latency targets. Local Node servicing remains separate from the patched Node 24.22.2 release image and CI runtime. See progress for subsequent runs and exact source verification.

Remaining production work includes a synthetic staging dataset with recorded distributions/total sizes, pinned deployed artifacts, network/client/region/cache conditions, longer repeated stepped workloads, cold/warm and large-tenant paths, writes/imports/search lag, noisy neighbors, concurrent access changes and fault/recovery tests. Record API/database/worker CPU/memory/connections, errors, queue/dead letters and completion latency with redacted telemetry. Agree capacity/error/latency budgets and evaluate them against actual staging measurements before any SLO or pilot-capacity claim. Actual staging execution requires an authorized environment; dataset/harness/telemetry/quotas and fault-scenario code can continue before accounts.

On 2026-11-03 the scoped native-HTTP implementation completed another 240 requests/concurrency 8 with zero failures: p50 7.43 ms, p95 15.41 ms, p99 271.5 ms, maximum 455.02 ms. Each of the six groups had forty valid responses. Tenant A returned 50 organizations, 50 assets and one search hit per page; tenant B returned one organization, 30 assets and one search hit. These are first-page counts, not total dataset sizes. Repository checkpoint was modified 194c506; client hardware/runtime and the retained development stack were unchanged. Transport, caches/JIT and data changed between experiments, so the difference is not a measured performance improvement. [Node's HTTP agent documentation](https://nodejs.org/docs/latest-v24.x/api/http.html#built-in-proxy-support) explains why an explicit direct agent is needed when ambient proxy mode is enabled.
